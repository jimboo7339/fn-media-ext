# 观影时间线 · 设计方案

> 基于 `tmp/` 三份数据库的分析结论（见 [data-analysis.md](data-analysis.md)），结合你确认的 6 个约束。
> 配图为真实数据渲染的设计预览：[时间线](images/timeline.png) · [剧集矩阵](images/matrix.png)。

## 0. 一句话结论

**一个 Docker 容器 + 一个 Python 进程**：只读挂载飞牛影视的数据库目录，把三份库复制成本地快照，派生出一张 `watch_event` 表，用 FastAPI + Jinja 服务端渲染三个页面（时间线 / 剧集矩阵 / 设置），账号与排除项存在自己的 SQLite 里，海报直接读飞牛已刮削的本地图片。

不引入 Node、不引前端框架、不写回任何原始库。

## 2. 时间线：我推荐这个形态

![时间线](images/timeline.png)

一屏分三块，从「概览」到「细节」：

1. **活跃热力带**（顶部）：每人一行 × 近 90 天，格子颜色深浅 = 当天看了几集。一眼看出谁在哪段时间活跃、谁断更了。
2. **观看流**（主区）：按天倒序，一条记录一行——海报、剧名、`S01E08`、单集标题、谁看的、几点、进度条。今天/昨天有特殊标记。
3. **正在追**（右栏）：还没看完的剧，按最近观看排序，带进度；下面是「多人共看」和「被排除的内容」。

配套的交互：顶部切 7/30/90 天/全部；左侧点账号或媒体库即时过滤；点某天的格子跳到那一天的观看流。

### 2.1 为什么不做甘特图

我先做了一版「用户泳道 × 时间轴」的甘特，发现两个硬伤：

- 一次观看只有几十分钟，铺在 90 天的时间轴上不到 1 个像素，几乎不可见；
- 如果改成「一部剧从首看到最近」的长条，又会把「断更两个月」画成连续追剧，**是在骗自己**。

而数据本身是「状态」而非「事件」（每人每集只有一行），所以按天聚合的**卡片流**才是它最诚实的表达方式。想保留时间轴感，就用顶部那条热力带。

> 如果你还是喜欢甘特，可以留作后续的「追剧周期」视图：条 = 一部剧的首看→末看，鼠标悬停显示中间的空档。等主线做完再加，不影响架构。

## 3. 剧集矩阵：回答「谁看过哪些剧」

![剧集矩阵](images/matrix.png)

行 = 剧，列 = 用户，格子 = 这个人看了几集、看到第几集、最后一集的进度。全时段统计，不受时间范围影响。

这张表解决了卡片流最大的问题：**没法横向对比**。`剧A` 谁看的多、`剧B` 是不是两个人一起追，一眼就能看出来。数据量只有 30 多部剧，一屏能放下大半。

## 4. 排除功能

设置页两组开关，勾掉即生效：

- **媒体库**：`adult`（成人）、`幼小教育`（孩子的动画片）…… 默认排除 `adult`。
- **账号**：`adult`、`user4`、`test01`…… 默认排除 `adult`。

规则：

- 排除是**展示层过滤**，原始数据不动，随时可以勾回来；
- 时间线右栏会显示「已排除 38 条记录 · 媒体库：adult」，让你知道过滤了什么，而不是悄悄消失；
- 剧集矩阵、KPI、热力带全部走同一套过滤，不会出现「时间线里没有、统计里还有」的穿帮；
- 配置存在 `data/app.db`，重启不丢。

> 顺带一提：库里没有任何 adult 标记（`item.adult` 全 0、`mediadb_config.include_adult` 全 0），所以**没法自动识别**，只能靠你手动指定。首次启动我会预置 `adult` 两条，其余你自己加。

## 5. 海报：可以直接复用，不用 TMDB

这是这轮排查里最有价值的发现：

`item.posters` 存的是 `/2f/14/RXFg9YOl...webp`，而 TMDB 归档 `item_archive.poster_path` 存的是 `/RXFg9YOl...webp`——**同一个文件名，没有 `https://image.tmdb.org` 前缀**。

也就是说，飞牛刮削时已经把图下载到本地了，归档里记录的是本地缓存路径，不是 TMDB 路径。所以：

- ✅ 海报可以直接从 NAS 读，**不需要联网、不需要 TMDB key**；
- ✅ 分辨率、清晰度就是飞牛里看到的那些，不会变；
- ⚠️ 必须额外挂载 meta 目录（见 §8），否则只能退化成色块。

**解析策略**（按顺序，命中即止）：

1. `<img_root>/2f/14/xxx.webp` —— 直接用 `item.posters` 的相对路径拼；
2. `<img_root>/<basename>` —— 归档里的裸文件名；
3. 启动时遍历一次 meta 目录，建 `basename → 路径` 索引，按文件名反查（**最稳**，不依赖目录分片规则）；
4. 都没找到 → 生成色块占位（按剧名哈希取色，就是预览图里那些方块）。

设置页会显示「海报自检：已解析 27 / 34 部剧」，如果明显偏低，把 `TRIM_IMG_ROOT` 指到正确的目录即可。

## 6. 数据层

### 6.1 目录约定

| 容器内路径 | 挂载 | 用途 |
|---|---|---|
| `/data/trim` | 读写挂载 | `trimmedia.db` / `trimmedia_ext.db` / `trimactivity.db`（WAL 库，需要能建 `-shm`；只读由连接串 `?mode=ro` 保证） |
| `/data/meta` | `:ro` | 海报图片目录 |
| `/app/data` | 读写 | `app.db`（账号、排除项）、`snap/*.db`（快照） |

### 6.2 快照

不直接查生产库，原因有三个：WAL 模式下只读连接可能因为 `-shm` 不可写而报错、长时间查询会占锁、多份库需要一致性视图。

第一条在部署时被实测证实：`/data/trim` 加 `:ro` 时，`mode=ro` 打开源库直接报 `unable to open database file`（只读目录里建不了 `-shm`），实时在线页只能退回快照。所以**挂载不加 `:ro`**，只读完全由连接串保证——只读连接不写主库、不 checkpoint，只会在目录里创建/映射 `-shm`。

做法：启动时 + 每 10 分钟（可配）+ 手动点「刷新」，用 SQLite 的 `backup()` 把三份库复制到 `snap/`，之后所有查询都读快照。单次约 40 MB，NAS 上不到 1 秒。

### 6.3 派生表 `watch_event`

```
id            INTEGER PK
user_guid     TEXT
user_name     TEXT
show_key      TEXT      -- trim_id，没有则退回 TV guid / item guid
show_title    TEXT
item_guid     TEXT
item_type     TEXT      -- Episode / Movie / Video
season        INTEGER
episode       INTEGER
episode_title TEXT
event_time    INTEGER   -- 毫秒 UTC，取 update_time（最近观看）
first_time    INTEGER   -- create_time
watched       INTEGER
position      INTEGER   -- 秒
duration      INTEGER   -- 秒，可能为 0
pct           INTEGER   -- 0-100，算不出来就是 NULL
library       TEXT
poster        TEXT
```

每次刷新重建（400 行，毫秒级）。查询层再套一层排除过滤。

### 6.4 三个必须处理的细节

| 细节 | 处理 |
|---|---|
| 时间单位混用 | 导入时统一转毫秒 UTC；`runtime` 是分钟、`ts`/`duration` 是秒，单独标注 |
| 同一部剧多条 `TV` 记录 | 按 `trim_id` 归并，否则 `剧C` 会被拆成两部（17 集 + 11 集） |
| 批量标记 | 同一用户 60 秒内 ≥5 条 → 折叠成一张「批量标记 N 集」的卡片，不铺 152 行 |

## 8. 部署

```yaml
services:
  watch:
    build: .
    image: trim-watch:1
    container_name: trim-watch
    restart: unless-stopped
    ports: ["8787:8787"]
    environment:
      TZ: Asia/Shanghai
      TRIM_DB_DIR: /data/trim
      TRIM_IMG_ROOT: /data/meta
      SNAPSHOT_MINUTES: "10"
      APP_SECRET: "换成随机字符串"
    volumes:
      - /usr/local/apps/@appdata/trim.media/database:/data/trim
      - /vol1/@appmeta/trim.media:/data/meta:ro
      - ./data:/app/data
```

要点：

- `/data/meta` 加 `:ro`；`/data/trim` **不能加**——源库是 WAL，只读挂载下 SQLite 建不了 `-shm`，会直接报 `unable to open database file`。不写坏飞牛这件事改由应用层保证：所有源库连接都用 `?mode=ro`；
- `media_server.meta_dir` 记录的是 `/vol1/@appmeta/trim.media`，海报应该在里面。不确定就先只挂 `database`，页面会退化成色块，不影响使用；
- 在飞牛 Docker 应用里，把上面两个宿主机路径加进「文件夹」映射：海报目录勾只读，数据库目录**不要**勾只读（原因见上）；端口 8787 随便换；
- 建议再加一条 `healthcheck: curl -f http://localhost:8787/health`。

## 11. 落地情况

M1–M4 已完成，`README.md` 是使用说明，`docs/images/app-*.png` 是真实数据下的界面截图。

| 里程碑 | 状态 | 落点 |
|---|---|---|
| M1 快照 + 派生表 + 排除 | 完成 | `app/ingest.py`、`app/db.py` |
| M2 时间线 | 完成 | `app/queries.py`、`templates/timeline.html` |
| M3 矩阵 + 海报 | 完成 | `app/posters.py`、`templates/matrix.html` |
| M4 登录 / 设置 / Docker | 完成 | `app/auth.py`、`Dockerfile`、`docker-compose.yml` |

实现时和设计稿的几处偏差：

- **批次折叠**：设计里没提，实现时发现同一个人 60 秒内连续标记 ≥5 集会刷屏（有一批 152 条），所以折叠成一张卡片，`bulk_group`/`bulk_size` 存在事件表里；
- **剧集合并**：同一部剧在源库里可能有 3 条 `TV` 记录（不同季、不同媒体库副本），统一按 `trim_id` 归并到「集数最多」的那条，矩阵和时间线才不会拆成三行；
- **元数据取 `tv`/`movie` 节点**：`item_archive` 把每一集都挂在同一个 `trim_id` 下，直接取最后一行会拿到单集标题，必须只认 `tv`/`movie`；
- **进度为 0 不显示**：`ts=0` 的行（标记已看但没真正播放）不画进度条，改显示 `—`，否则平均进度会被拉到个位数；
- **快照按 mtime 跳过**：源库没变就不重复复制（三个库约 42 MB），同步从 1.4 s 降到 0.35 s。

## 12. 实时在线：能做到什么程度

飞牛影视没有「在线用户」这类接口，能拿到的只有三类落库的时间戳：

| 信号 | 表 | 单位 | 用途 |
|---|---|---|---|
| 播放进度心跳 | `item_user_play.update_time` | 毫秒 | 判断「正在看」 |
| 访问日志 | `trimactivity.db` / `user_activity_log.time` | 秒 | 判断「30 分钟内活跃」 |
| 登录令牌 | `trimactivity.db` / `user_token.update_time` | 秒 | 判断「有什么设备在线」 |

阈值：**5 分钟**内有进度上报算「正在看」（飞牛在暂停时不上报，长暂停会被判定为离开），**30 分钟**内有访问算「活跃」，**12 小时**内有令牌算「在线设备」。这些数字写在 `app/live.py` 顶部，想调直接改。

为什么不用快照：快照是 10 分钟一次，看实时状态没意义。`/live` 每次请求都开一个新的只读连接直查源库，结果缓存 3 秒防止多标签页放大查询；连接失败就退回快照并在页面顶部说明，而不是假装实时。（前提：`/data/trim` 可写挂载，见 §6.2。）

隐私：接口里不返回 token，IP 只保留前三段，设备型号原样显示（`app_name` 映射成「网页 / Android / iOS / 电视端 / Kodi」）。

## 13. 主题切换

一份 CSS、两套变量。`html[data-theme="light"]` 只覆盖 `:root` 里的设计令牌（背景、面板、文字、边框、海报底色、热力格、按钮、输入框……），组件规则里不出现写死的颜色——这是这次改动里唯一需要认真做的重构。

- 偏好在 `<head>` 里用一段内联脚本读 `localStorage`（键 `fnxt.theme`，值 `auto|light|dark`），在样式表之前就把 `data-theme` 写到 `<html>` 上，避免刷新时先黑后白；
- `auto` 用 `matchMedia('(prefers-color-scheme: light)')` 解析，并监听 `change`，系统切换时页面跟着变，不需要刷新；
- 三个按钮放在侧栏底部（登录 / 初始化页在右上角），点击只改 `localStorage` 和属性，不重载页面；
- 链接加 `?theme=light|dark|auto` 可以直接指定并记住，方便分享某个主题下的截图。

## 14. 单剧详情页与用户画像

两个下钻页面，入口是所有已经出现剧名和用户名的地方：时间线行（海报与剧名、用户名）、矩阵的行头与列头、实时在线的正在观看/最近播放/设备表。链接在模板里用 `|urlencode` 生成，中文用户名不需要额外处理。

### 14.1 `/show/{show_key}`

`show_key` 就是 `watch_event.show_key`（归并后的 `trim_id`，缺失时退回条目 guid）。聚合全部时间段的数据（不受时间线 7/30/90 天筛选影响），得到：

- **谁在看**：每人一行——看到的最后一集、已看集数、最近一次时间、进度条。
- **分集明细**：每集一行——集号、单集标题、看过的人（头像叠放）、进度或「已看」、最近时间。
- **最近观看**：该剧最近 20 条流水。

两个刻意的口径选择：

- 进度条表示**看到的集数占全剧集数的比例**，不是 `已看 / 看过`。后者会得出「user3 看过 5 集、标记已看 1 集 = 20%」这种反直觉的数字；用 E14 / 15 集 = 93% 才符合「追到哪了」的直觉。
- **全剧集数**从快照库现查（`item → Season → TV`，按 `trim_id` 匹配），不写进 `app.db`。这样详情页能给出「已看 2 / 15」，但代价是每个详情页多一次只读连接；查询很小（一次 COUNT），失败时退化为不显示总数。

「已看」的判定沿用飞牛的标记：`watched = 1` 或进度 ≥98%。

### 14.2 `/user/{name}`

- KPI：观看记录、活跃天数、在追剧集、观看时长
- 媒体库分布（口味）、24 小时时段直方图、星期分布
- 在追清单（最近一次记录尚未标记看完）、整部看完的剧、共同剧集排行
- 最近 20 条流水

口径：

- **观看时长**是「每集记录的最大播放进度」求和，属于**估算**：飞牛只留每集最后一处进度，跳过片头或来回拖动都会影响结果。页面底部写明了这一点，不假装是实际播放耗时。
- **整部看完**要求该用户看过的每一集都被标记已看，且至少 2 集。只看单集「已看」标记会得出「刚开一集就说看完了」的假信号（`watched` 是单集维度，不是整剧维度）。
- **时段/星期分布**按每条记录的事件时间统计，`update_time` 是毫秒，统一除以 1000 再转时区。

### 14.3 排除与隐私

两个页面都复用 `db.exclusions()`：被排除的账号或媒体库的记录不参与聚合；如果聚合结果为空，路由返回 404 文案（「没有这部影片的观看记录」）而不是空页面。默认排除的 `adult` 库与账号因此点不进去。

用户画像是按用户名聚合的，不含 IP、设备、token——那些只存在于实时在线页面的只读查询里，不落 `app.db`。

## 15. 分析页面：搜索 / 回顾 / 弃剧 / 排行 / 一起看 / 体检

六个页面（其中「一起看」并入剧集矩阵），共用一套前置规则：先 `_allowed()` 过滤掉被排除的账号与媒体库，再做聚合。所有页面都不碰源库——只有 `live.py` 那条实时路径会直连源库，其余全部读 `app.db`。

### 15.1 搜索 `/search`

服务端搜索，`?q=` 可分享。匹配范围是剧名、单集标题、季集编号（`S01E14`）、成员名，结果分「剧集 / 成员 / 观看记录」三块，记录最多列 60 条。

搜索需要同时给出「剧」这一层的结果，所以复用了两个索引函数：`_show_index()`（按剧聚合）和 `_people_index()`（按人聚合）。这两个函数后面被回顾、排行、体检四个页面一起用，是这次改动里最值钱的重构——之前每个页面各写一遍聚合。

原来时间线上按 `/` 会弹一个 `prompt()` 做前端过滤，搜完刷新就没了；现在 `/` 只是把焦点移到侧栏搜索框，真正的过滤在服务端。

### 15.2 月度 / 年度回顾 `/recap`

`?mode=month|year&p=2026-10|2026`，`p` 缺省时取有数据的最后一个区间，`‹ ›` 在数据覆盖的区间之间移动。

一个刻意的限制：**环比只在上一区间基数足够大时显示**。事件数少于 10 条、时长少于 60 分钟时返回 `None`，页面上不显示百分比。原因很实际——2025 年整年只有 2 条记录，直接比较会得出「+17700%」这种既不真实也没用的数字。

柱状图在月视图下是每日、年视图下是每月，取峰值做归一化。

### 15.3 弃剧分析 `/dropouts`

判定：某用户在某剧上的**最后一条记录**没有标记已看、进度也没到 98%，且距今天数 ≥ 窗口（7/30/90/180）。

表格分两列：「看过」是有播放记录的集数，「已看」是其中被标记看完的集数。这个区分是必需的——「看过 24 集、已看 0 集」（追到第 24 集弃了）和「看过 1 集、已看 0 集」（点开就弃）是完全不同的故事，合成一列「0 / 24」就看不出来了。

`watched` 是单集维度而不是整剧维度，所以这里判断的是「最后停在哪儿」，不是「整部剧看完没有」。

### 15.4 数据排行 `/stats`

成员和剧集两个维度，各自按时长和记录数排。时长沿用详情页那套估算：每条记录按集取最大播放位置再求和。

记录数和时长的排名会不一致，这是数据本身的特性而不是 bug：有人习惯用「标记已看」批量刷进度，这类记录通常没有播放位置。页面底部把这一点写出来了，避免读者以为算错了。

排序时会过滤掉时长为 0 的剧，否则排行榜末尾会是一排「0 小时」。

### 15.5 一起看 / 撞车（并入 `/matrix`）

按 `(show_key, item_guid)` 分组，同日窗口 24 小时，窗口内出现 ≥2 个不同用户就算一组。然后按时间差再分两档：

- 相差 ≤3 小时 → **几乎同时**，可以合理地说「一起看」；
- 3–24 小时 → **同一天**，只能说同一天看的同一集。

还有一条硬规则：**跨零点的组合直接丢弃**。早 20:26 与次日 12:29 相差 16 小时，既不是一起看也不是同一天；早期版本把它们放进「同一天」还让时间标签倒着显示（`20:26 – 12:29`），这是实现过程中实际发现的错误。

### 15.6 媒体库体检 `/libraries`

各库的记录、剧集、人数、时长、海报路径覆盖、最近活动、搁置天数，外加一批检查：

| 检查 | 判据 | 为什么值得看 |
|---|---|---|
| 海报文件 | `posters.resolve()` 能否找到文件 | **路径存在 ≠ 文件存在**：`watch_event.poster` 存的是库里的相对路径，容器没挂载图片目录时全是空的。设置页和这一页都会如实显示 `0 / 22` |
| 时长未知 | 该剧所有记录 `duration = 0` | 这些剧算不出进度百分比，页面上显示「—」 |
| 跨库重复 | 同一 `trim_id` 出现在多个媒体库 | 会在矩阵里合并成一行，避免重复计数 |
| 从未被看 | `catalog` 里事件数为 0 的库 | 挂了但没人用的库 |
| 长期未动 | 最近记录 ≥90 天 | 与弃剧分析互补：这里看剧，那里看人 |
| 排除项 | `exclusion` 表 | 明示哪些内容被有意隐藏了 |

「未归属」作为一个伪媒体库出现（`item_ancestor` 里找不到 `MediaDB` 祖先的记录），页面上带 `无媒体库归属` 标签，不隐藏这个问题。

## 16. 数据新鲜度：定时 + 按需两层

页面读的 `app.db` 是派生表（源库 42 MB → 派生表 204 KB），所以问题不是「能不能实时读」，而是「多久重建一次」。

| | 数据来源 | 新鲜度 |
|---|---|---|
| `/live` | 每次请求直连挂载的源库（3 秒缓存） | 秒级 |
| 其余页面 | 派生表 `app.db` | 定时 10 分钟 + 访问时按需补 |

实测开销：带快照复制的全量同步 1.66 秒（大头是复制 42 MB），源库 mtime 没变时跳过复制只要 0.25 秒。页面查询走的是 204 KB 的派生表，与源库大小无关。

`ingest.maybe_sync()` 挂在 HTTP 中间件上，规则是：

1. 数据比 `SYNC_STALE_SECONDS`（默认 60）新 → 什么都不做；
2. 超过 → **起一个后台线程补同步，页面不等**，先把现有数据发出去（实测页面 55–75 ms，不受影响）；
3. 陈旧超过 `SYNC_BLOCKING_SECONDS`（默认 1800，正常不会发生，除非定时循环停摆）→ 等它同步完再出页面，用 `SYNC_BLOCKING_WAIT`（默认 5 秒）兜底，防止挂载异常把请求拖死；
4. 15 秒内只尝试一次，避免多个标签页同时打开引发同步风暴；`_LOCK` + `_STATE["busy"]` 保证同一时刻只有一次真正在跑。

`/static`、`/img`、`/partials`、`/favicon.ico`、`/health` 不触发——尤其 `/health` 被 Docker HEALTHCHECK 每分钟打一次，不排除的话会变成每分钟同步一次。实时在线的 `/partials/live` 每 10 秒轮询一次，它不读派生表，也不需要触发。

`app.db` 是 WAL 模式（`busy_timeout=5000`），后台写不会阻塞页面读。

## 17. 侧栏成员列表：主次动作分开

一开始侧栏的成员行整行就是一个筛选开关——点一下把这个人从时间线里排除。实际用起来不对：**进某个人的详情页才是主要动作，筛选是次要动作**，而整行点击把次要动作放在了主要位置上（还要先划掉再点进详情，绕）。

改成一行两个动作：

- 点名字（占整行大部分）→ `/user/{name}` 详情页；
- 点右侧漏斗图标 → 切换这个人在时间线/矩阵里的可见性。

漏斗默认只在悬停时出现，避免六行小图标把侧栏弄花；成员处于「被隐藏」状态时常显，这样随时能点回来。被隐藏的行保留划线 + 降透明度，状态没有变，只是换了个触发位置。

媒体库列表保持整行筛选：库没有详情页，整行点击就是它唯一的动作，硬拆成两个反而多一次无意义点击。两边行为不同是有意的，`title` 文案也各自说明了。

由此带来两个附带的改动：

- `/user/{name}` 现在也渲染侧栏的成员/库列表（`queries.default_filters()`），当前成员带 `.cur` 高亮，等于「你在看谁」的指示器，也方便直接切到别人；
- 用户详情页顶部加了「只看 xxx 的时间线」按钮（`/?u=xxx`），筛选能力仍然可达，只是不再占据侧栏的点击位。

其他分析页（`/stats`、`/recap`、`/dropouts`、`/libraries`、`/search`）不渲染这两个列表：它们是全局页面，列表在那里点了不会有任何过滤效果，摆着只会误导。

## 18. 界面改版：卡片化 + 移动端

原来的界面能用，但有两个硬伤：

1. **手机上侧栏整个摊在页面顶部**。导航、用户筛选、媒体库筛选全都排在内容前面，手机上要先滑过 600 多像素才看得到第一条记录；
2. **视觉上没有层级**。所有东西都是「1px 边框 + 一块底色」的平面矩形，深色主题里连阴影都没有，看起来像后台管理系统而不是产品页。

### 18.1 设计系统

`static/app.css` 重写成一套 token 化的系统：

- **表面分层**：`--panel` / `--panel2` / `--panel3` 三级，加上 `linear-gradient(180deg, 白色 3.5%, 透明)` 的高光层，卡片才有「面」的厚度；页面背景额外叠两团径向光晕，避免大面积纯色的塑料感；
- **描边**：不用实色边框，用 `rgba(255,255,255,.075)` 这样的半透明描边，深浅主题共用一套逻辑；
- **圆角**：8 / 11 / 14 / 18 / 24 五档，别再随手写 7px、9px；
- **阴影**：三档 + 一档品牌色投影（`--sh-accent`），悬停时卡片浮起 1~2px；
- **数字**用渐变文字（`background-clip:text`），KPI 卡的数值因此有了视觉重量；
- **动效**统一到 `--t`（0.22s）/ `--t-fast`（0.14s）两条曲线，并遵守 `prefers-reduced-motion`。

浅色主题只覆盖 token，不重写任何规则——这是从一开始就定下的规矩，这次改版验证了它确实省事。

### 18.2 移动端形态

- **侧栏变抽屉**：≤900px 时侧栏 `position:fixed` + `translateX(-102%)`，顶部条上的汉堡按钮打开，遮罩点击或 Esc 关闭，抽屉里的链接点完自动收起；从窄屏拉宽到宽屏时复位，避免侧栏被锁住；
- **顶部条**：毛玻璃（`backdrop-filter`）、粘顶、左侧汉堡、中间品牌、右侧搜索与主题循环按钮；
- **底部导航**：五个大按钮（时间线 / 实时 / 矩阵 / 排行 / 更多），「更多」打开抽屉——单手可达，不用在抽屉里找；
- **时间线行**在 ≤640px 变成三段式卡片：海报 + 剧名 / 集号 / 单集标题 / 媒体库，用户与时间一行，进度条独占一行；
- **表格卡片化**：所有 `.tbl` 在手机上变成「字段名 — 值」的卡片列表，字段名来自新增的 `data-label` 属性（由表头自动生成，见下），不用左右滑动；矩阵表列数太多，保留横向滚动但剧名列 `position:sticky` 钉在左边；
- 触控目标放大，正文 15px，底部条高度算上 `env(safe-area-inset-bottom)`。

### 18.3 表格标签怎么维护

给 49 个单元格手工写 `data-label` 显然不可维护。做法是：表头的 `<th>` 文本就是标签，脚本按「同一张表内第 N 个 `<td>` 对应第 N 个 `<th>`」批量写入 `data-label`；带 `colspan` 的行（空状态提示）跳过。加了列就重跑一次脚本，不会漏标。

### 18.4 验证方式

用 headless Edge 截图逐页比对桌面 / 手机 × 深浅两套主题。过程中踩到一个坑：**Windows 上 headless Edge 的窗口宽度有下限（约 492px），而截图按请求宽度裁切**，于是看起来「右边被切断」，实际是裁图假象。判断依据是往页面里注入 `position:fixed;inset:0` 的荧光绿边框探针——它在图片右边缘出现，说明布局宽度与截图宽度一致；再用 `document.documentElement.scrollWidth` 确认没有横向溢出。以后做移动端截图直接用 520px 宽。
